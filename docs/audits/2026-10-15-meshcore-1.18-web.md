Fecha: 2026-10-15. Alcance: inspección de SPA, controladores REST, eventos WS y
límites de publicación administrativa. Esta auditoría complementa la verificación
del tag oficial; el checkout local de `reference/` no se actualizó. Las propuestas
siguientes no representan capacidades ya implementadas.

  `AdvertDataParser::isValidName`; el checkout local anterior no contiene todavía

- `CMD_SET_ADVERT_NAME` binario copia el nombre y añade terminador, sin aplicar
  esa lista (`reference/meshcore/examples/companion_radio/MyMesh.cpp:1212`).
  Endurecer indiscriminadamente `firmware_name_valid` rompería nombres de canal y
  contactos admitidos actualmente: sus consumidores son
  `contacts_controller.py:34` y `channels_controller.py:349`. La validación del
  CLI remoto ya rechaza esos caracteres (`repeater_manager.py:550`). Se deben
  conservar validadores según operación y confirmar el comportamiento en 1.18.
- TCP ya existe: `src/serial/sdk_adapter.py:321` consume `tcp://host:port` y llama
  al transporte TCP oficial; `config.py:81` carga `SERIAL_PORT`. Falta una interfaz
  web para cambiar el transporte, no el transporte entero.
- La consola local tiene comandos sintéticos y consultas reales al SDK:
  `src/admin/cli_command_executor.py:146` consulta estadísticas de radio mediante
  `get_stats_radio`. No es correcto calificar toda la consola como simulada.
- La SPA admite cuatro dígitos en los campos de frecuencia; no tiene un máximo
  HTML de 960 MHz (`src/web/static/index.html:949` y `:2371`). Admitir un número
  no demuestra capacidad física del transceptor.

## Matriz de contratos actuales y evolución

La autenticación de la aplicación se aplica en middleware ASGI con cuenta/sesión
o credencial admitida, y CSRF para mutaciones con cookie
(`src/web/authentication.py:332`). Es independiente del login administrativo RF
del dispositivo. Las rutas abreviadas conservan los aliases de
`src/web/api_router.py:61`.

| Función | Contrato y consumidor actual | Evolución conveniente | Condición de aceptación |
| --- | --- | --- | --- |
| Estado local | `GET /api/node/config` → `/api/config`; `{status:"ok",data:config}`; `settings.js` | Mostrar versión del protocolo, versión de firmware, transporte y capacidades diferenciadas | No inferir LR1121/WiFi sólo a partir de un número de versión |
| Configuración local | `POST /api/node/settings`, `/api/node/config` → `/api/config`; `ConfigController.set_local_config` | Añadir controles concretos cuando exista comando SDK/firmware probado | Prevalidar el lote completo; conservar baseline, error y confirmación del dispositivo |
| Radio local | `POST /api/node/config/radio`; `local_config_executor.py` usa API Companion | Mantener API binaria para campos ya soportados; ampliar sólo capacidades verificadas | No sustituir escritura inmediata binaria por CLI que sólo guarda preferencias |
| CLI local | `POST /api/admin/command` → `/api/admin`; `{action,command/cmd,...}`; respuesta `{status,result,response,message}` | Lecturas nativas seleccionadas de 1.18 y resultados estructurados | No reenviar automáticamente comandos desconocidos al firmware; `advert`, cambios RF, reboot y secretos requieren rutas explícitas |
| Transporte Companion | `SERIAL_PORT=tcp://host:port` en configuración del proceso; estado expone `serial_port` | Selector USB/TCP y dirección validada, con estado conectado/desconectado | No mezclar servidor TCP del bridge con conexión TCP al dispositivo; validar host/puerto, IPv6 y reconnect antes de exponer cambios web |
| Configuración remota | `POST /api/repeater/remote/config`; `{target_node,password,params}`; `repeater.js:802` | Controles `CommonRadioPrefs` por versión/capacidad y rol | Mantener `dispatched`, `saved`, `applied` y error parcial; lectura bajo demanda |
| Terminal remoto | `POST /api/admin/repeater`; `{target_node,action,params,password}`; `repeater.js:1610` | Ayuda de comandos 1.18 filtrada por destino | Bloquear `ROOM set repeat on` en backend y formulario; validar también CLI libre y lote |
| Hash de ruta | `GET/POST /api/node/path_hash_mode` → `/api/config/path_hash_mode` | Reutilizar UI y contrato existentes | No añadir un segundo control de idéntico estado para 1.18 |

| Telemetría pasiva | WS genérico → `EVENTS.RX_PACKET`; `repeater.js:857` consume `repeater_response/repeater_telemetry` | Normalizar evento 0x8C en backend y mostrar muestras con emisor/timestamp | No realizar consulta RF de seguimiento por recibir telemetría |
| Datagrama binario/raw | Sin controles web dedicados auditados | Posponer salvo caso de uso explícito | No tratar payload binario como chat ni habilitar inyección arbitraria desde un formulario |

Las respuestas de rechazo administrativo pasan por `BaseController.command_failure`
(`base.py:91`): se preservan fallos/errores parciales, y `_remote_failure` admite
`dispatched` como despacho, no como aplicación confirmada
(`repeater_controller.py:18`). La nueva UI debe mantener esas distinciones.

## Secretos: fallo corregido y límites

Se corrigió la redacción del nombre real `wifi.pwd` y del alias histórico
`wifi.password` en `src/protocol_types.py`. También se ocultan claves de mapping
con esos nombres y comandos con prefijo de correlación `AA|`. Se conserva la
redacción recursiva sin mutar el objeto privado.

En `src/web/static/js/modules/repeater.js`, `_redactRemoteCommand` ahora oculta
ambas grafías antes de imprimir la orden y antes de decidir si puede guardarse
en el historial. Los dos puntos de entrada de terminal ya consultan ese helper
(`repeater.js:254`, `:656`); el envío sigue usando el comando privado original.

Sinks inspeccionados:

| Salida | Protección existente / cambio |
| --- | --- |
| Log TX administrativo | `repeater_executor.py:183` llama `redact_sensitive_command`; recibe el fix central |
| Estado MQTT administrativo | `admin_handler.py` y `cli_command_executor.py:140` usan redacción recursiva; recibe el fix de comandos y mapping |
| REST de configuración y WS `self_info` | `config_controller.py:111`, `:175` redactan configuración; recibe el fix de claves WiFi |
| Resultado CLI remoto | `cmd_dispatched`, listas de comandos y mapping de resultados usan helper central |
| Texto e historial de consola web | `_redactRemoteCommand` actualizado; los comandos sensibles no entran en el historial existente |
| Respuesta opaca de `get wifi.pwd` | Pendiente antes de habilitar una interfaz WiFi/CLI nativa; un texto sin etiqueta no puede redactarse sólo por regex |

La futura ruta nativa deberá clasificar el comando antes de ejecutarlo, ocultar
íntegramente la respuesta de una lectura de contraseña y propagar sensibilidad a
los futuros/eventos pendientes. La verificación del tag confirma que `get
wifi.pwd` devuelve `> %s` con la contraseña, mientras `set wifi.pwd` sólo confirma
la actualización. Además el SDK registra la orden completa a nivel DEBUG en
`run_cli_command`: debe protegerse también ese logger antes de exponer esta
operación. El ejecutor RF actualmente clasifica únicamente
`password`, `set guest.password` y `get guest.password`
(`repeater_executor.py:1332`, `:1367`, `:1511`). Ampliar el acceso a WiFi sin
ampliar primero esa clasificación expondría secretos por respuestas asíncronas.
La función de regex no constituye por sí sola una garantía global de privacidad.

### Revisión cruzada de whitespace, aliases y formularios

Una segunda revisión encontró que `set[ _]` en backend permitía filtrar secretos
con dos espacios (`set  pin 654321`), mientras el ejecutor local usa `split()` y
sí admite esa separación. El patrón ahora acepta whitespace múltiple o underscore,
y espacio tras un prefijo de correlación. Esto protege también texto de comandos
rechazados; no autoriza una gramática CLI nueva en firmware.

El helper frontend ahora conserva protección para `identity` y cubre los aliases
del backend: `admin.password`, `prv.key`, `prv_key`, `pin`, `ble_pin`, `blepin`,
`devicepin`, `set_password`, además de las claves WiFi/guest/password/login.
Acepta espacios iniciales y después de `AA|`, sin modificar el comando privado
que se envía al transporte.

Las nuevas regresiones primero produjeron **6 failed, 6 passed**, incluido un caso
real de formulario que imprimía `AA| set admin.password isolated-quick-secret`
en el DOM. Tras el parche, **46 passed en 9,44 s** en los tres módulos de
privacidad con `--basetemp=artifacts/qa-wifi-redaction-revision-green`.
El test de navegador usa los dos formularios reales, intercepta únicamente
`/api/repeater/remote/**`, comprueba el texto de consola y el recall con ArrowUp,
y verifica que el payload privado conserva la orden original. No usa radio ni
broker de producción. El test Node se renombró para atribuirle sólo la redacción
que realmente ejercita, sin reconstruir un historial artificial.

El fixture compartido ya fue reparado por el principal para servir PNG neutro
únicamente a los proveedores de tiles conocidos. El caso de navegador anterior
dejó de fallar por esos recursos. Ruff pasó y mypy estricto pasó para el módulo
de producción y la regresión; se regeneraron otra vez los tres artefactos
frontend afectados.

### Cancelación intencional de lecturas durante QA

La suite general se detuvo en el teardown de navegación a Analítica: el cuerpo
pasaba, pero dos lecturas locales reportaban `net::ERR_ABORTED`. Se reprodujo en
aislamiento. `AnalyticsModule.fetchAnalytics` cancela su generación anterior con
`AbortController`; una entrada de pestaña y el evento `meshcore:station_changed`
pueden reemplazar la lectura iniciada durante `init()`. Esperar el primer estado
`ready` antes de navegar no eliminó los aborts ya observados durante el arranque.
No se modificó este comportamiento de producción.

El fixture ahora observa `signal.abort` en un wrapper que delega sin alterar
input, init, signal, respuesta o promesa de `fetch`. Sólo se admite un
`net::ERR_ABORTED` cuando coincide URL y método con una cancelación observada,
consumiendo una observación por solicitud fallida. Una cancelación desconocida,
otro método, otro error de red, HTTP de error y errores JavaScript conservan el
fallo de QA. Cuatro regresiones verifican esos límites; junto con el caso real
de navegación resultaron **5 passed en 10,99 s**. El test de navegación ahora
espera además datos analíticos en estado `ready` y fin de `aria-busy` después
del click.

Una ejecución anterior de todo `test_e2e_playwright.py` detectó otra causa
independiente: `test_e2e_dm_multi_recipient_isolation` no pudo cargar contactos
tras HTTP500 por `FileNotFoundError` en `AuthStore._restrict_files` (`os.chmod`
después de `exists`, al desaparecer un archivo SQLite auxiliar). Se entregó al
principal para diagnóstico y reparación de producción por separado; no se
silenció la respuesta500 en el fixture.

La ejecución posterior completa de `tests/test_e2e_playwright.py` con el fixture
instrumentado terminó con **14 passed en 140,46 s**, incluidos Analítica y DM.
No se reprodujo la carrera de chmod en esa ejecución; ese resultado no invalida
la evidencia500 anterior. Ruff pasó para los cuatro archivos QA modificados;
mypy estricto pasó para helper, regresiones de cancelación y E2E. Al incluir
`tests/conftest.py` en mypy, aparecen ocho errores de tipado previos sobre
`WebServerProtocol` y asignación de métodos, fuera de estos hunks; se registraron
sin relajar tipos ni ampliar cambios de producción.

`test_tile_server` accedía anónimamente a `/api/map/status`, ahora protegido por

## Capa 3 implementada: diagnóstico manual de firmware (2026-10-16)

Se añadió un bloque independiente en Ajustes → Telemetría y Estado, manteniendo
la consola del bridge. Consume `config.capabilities.firmware_cli` y presenta
protocolo Companion, versión firmware/SDK, modelo, transporte y disponibilidad
`unknown/absent/present` con razones traducidas. Los datos desconocidos no se
inventan; la descripción aclara que se leen preferencias informadas por firmware
y que pueden estar pendientes de reinicio, sin afirmar parámetros RF activos.

El selector sólo ofrece `get radio` y `get freq`, intersectados con los
`safe_commands` anunciados por backend. El formulario únicamente envía tras
submit manual `POST /api/admin` con
`{action:"cli",scope:"firmware",command:"get radio"|"get freq"}`, usando headers
de autenticación/CSRF existentes. El resultado espera el sobre administrativo
vigente `{status:"ok",result:{status:"ok",scope:"firmware",result:Texto}}`.
No hay consultas CLI por timer, navegación, refresco WS ni cambio de capacidad.
No se añadió una ruta `/api/cli` ni un socket nuevo.

El bloque usa `textContent` para metadatos, respuestas y errores. Conserva los
formularios modificados por el operador. Un cambio de identidad/capacidad,
desconexión o contexto de credenciales invalida resultados pendientes; una
respuesta tardía de otro contexto no se pinta. Tras HTTP503 se exige un snapshot
nuevo mediante el refresco/reconexión manual existente, mostrando error visible
sin identificar todos los503 como timeout y sin disparar un GET adicional.

Archivos: `settings.js`, `index.html`, diccionarios ES/EN de `i18n.js` y
`tests/test_meshcore_1_18_firmware_cli_browser.py`. El principal integra backend,
contratos y build final; este agente no modificó adaptadores, endpoints ni
artefactos minificados para esta capa.

TDD: el primer caso falló por ausencia del bloque; la regresión503 falló por
conservar capacidad presente. Tras implementar y mantener coherentes el snapshot
de conexión/capacidades del firmware virtual y la navegación offcanvas móvil,
los **7 casos pasaron en 50,34 s**. Cubren desktop1920×1080 y móvil390×844,
CSRF/payload exactos, ausencia de CLI automático, HTML literal, preservación de
drafts, capacidad ausente/desconocida, descarte de respuestas tardías y errores
422/503. Se inspeccionaron capturas bajo
`tests/artifacts/meshcore-1-18-firmware-cli/`; no se detectó overflow horizontal.
Ruff y mypy estricto de la regresión pasaron, y `node --check` de settings/i18n
terminó con código0. Esto acredita UI sobre estación virtual; no interoperabilidad
RF física ni accesibilidad WCAG completa.

## Secuencia de adopción propuesta

1. **Fundamentos y fixes sin RF:** corregir investigación, opcodes, parsers,
   redacción y clasificación pasiva. Conservar nombres según la operación real.
2. **Capacidades explícitas:** exponer en configuración local una matriz de lo
   que anuncia el dispositivo y lo que admite el SDK. Un firmware antiguo debe
   conservar el flujo actual. Mostrar motivo de controles deshabilitados.
3. **Lecturas nativas seleccionadas:** incorporar diagnóstico bajo demanda con
   timeout/correlación controlados. No ejecutar `get wifi.pwd` como diagnóstico.
   Conservar los comandos locales útiles que no son CLI del firmware.
4. **Controles de radio/remotos:** implementar cada parámetro validado por el tag
   oficial con su unidad, rango y semántica de aplicación; bloquear ROOM repeat
   donde corresponda. La capa RF debe mantener cola, cooldown y presupuesto.
5. **Transporte y WiFi:** exponer selección TCP con validación de dirección y
   recuperación de conexión; credencial como campo sólo de escritura y flag de
   presencia. No aplicar automáticamente un cambio que desconecte la sesión.
6. **QA por destino:** firmware 1.17 y 1.18, SDK mínimo/anterior soportado, USB y
   TCP virtuales, ROOM/REPEATER/LOCAL; navegador desktop/mobile aislado. Hardware
   real sólo en una validación posteriormente autorizada.

No se añaden timers, anuncios, consultas automáticas ni límites de airtime en
este parche. Para cada fase con emisión RF o cambio de radio se deben documentar
los tres puntos de AGENTS.md: paquetes/airtime, feedback/deduplicación y
persistencia/rearme. Los valores de límites o intervalos nuevos deben decidirse
con el usuario antes de implementar esa fase.
