# Auditoría del frontend: configuración local y remota

Fecha: 2026-10-03. Base inspeccionada: `81f4260eccf9bdec6c6f7ba9caca5322997f6eeb`. No se modificó producción ni referencias y no se publicaron cambios Git.

## Alcance y método

Se leyeron AGENTS.md, docs/README.md, docs/TESTING.md y las skills html-css-modern-js, web-ui-design-system, contract-openapi-sync y web-browser-inspection. Se revisaron HTML, SettingsModule, RepeaterModule, NodesModule, CSS, i18n y contratos de configuración. Se ejecutó solamente `reproduce_ui.py`, una reproducción dirigida que reutiliza las fixtures mantenidas de tests/conftest.py mediante sus funciones originales, sin ejecutar pytest ni una suite amplia.

La estación virtual utiliza datos temporales, VirtualMeshAdapter, MQTT simulado y un puerto loopback asignado por el SO. Chromium carga el HTML y los módulos reales. Todos los POST se interceptan antes del servidor; sus respuestas son simuladas, incluidas normalización y Problem Details 422. Las lecturas y WebSocket provienen de la estación virtual. Recursos externos se bloquean; se eliminan enlaces/scripts externos del documento servido. No hubo radio, broker ni estación operativa. El navegador, servidor y tareas se cerraron en finally.

Para aislar handlers sin registrarlos dos veces, SettingsModule recibe un contexto de auditoría y enlaza los elementos reales; el modal remoto se clona para quitar listeners anteriores y recibe una instancia del módulo real. La configuración de nodos se inyecta únicamente en el Map virtual del contexto. `unlockRepeaterAdminView()` se invoca expresamente para examinar formularios tras comprobar la puerta de autenticación: esto no prueba un bypass de autenticación ni una operación autorizada por el backend.

Entorno registrado: Windows, Python 3.12.14, Playwright 1.62.0, Chromium 151.0.7922.34. Ejecución final: exit 0. Archivos reproducibles: reproduce_ui.py, reproduction-results.json, run-output.txt y 26 capturas. El script no acredita interoperabilidad con firmware ni autenticación real del repetidor.

## Roles, capacidades y habilitación

- La ruta normal de Nodos sí condiciona Administrar a REPEATER/ROUTER (`nodes.js:452`, `:682`, `:728`). CLIENT/ROOM/SENSOR no reciben ese botón. Esto conserva la separación administrativa de repetidores y mensajería.
- La función pública openRepeaterAdminModal no tiene su propia comprobación de rol (`repeater.js:1133`). Invocarla para un CLIENT simulado muestra la puerta de contraseña. No demostró acceso sin autenticación. Conviene una guarda defensiva que use la clasificación canónica, también en backend.
- Autenticación remota bloquea/muestra formularios (`repeater.js:853`, `:891`); no equivale a capacidades por operación. Tras el desbloqueo artificial, radio/repeat/reboot permanecen habilitados incluso con capabilities:false inyectado. El objeto capabilities fue un mock prospectivo: el contrato local leído no exporta esa matriz; no se afirma que esté disponible actualmente ni que el frontend incumpla un contrato existente con ese nombre.
- Con radio_connected:false local permanecen activos SaveRadio, RepeatMode, DevicePin, PathHashMode, AdvertHop y Reboot (`settings.js:1023`, `:1733`). El código actual actualiza el badge/uptime, no los disabled por conexión. Evidencia en local_capability_controls del JSON.
- No restringir todas las opciones por rol del nodo local: una estación Companion puede cambiar de modo según firmware. La disponibilidad necesita rol/capacidad real/estado de conexión por operación, no sólo el badge Repetidor. Para recursos no conocidos: mostrar motivo de indisponibilidad y preservar lectura.

## Plan de reparación UI/UX

1. Contrato canónico por nodo: configuración confirmada, campos presentes, capabilities por operación, roles oficiales, estado conexión/auth, límites/unidades y error codes. Desconocido debe diferenciarse de0, false o vacío válido.
2. Formularios con borrador por nodo y sección; fusionar actualizaciones pasivas sin destruir dirty, reset al cambiar destino, no guardar campos desconocidos ni defaults ajenos. Serializar sólo cambios; confirmar con valores aplicados y errores parciales.
3. Máquina de estados: loading/ready/dirty/saving/applied/error/offline/unsupported. Guardar deshabilitado sin cambios o durante operación; capacidades deshabilitadas con explicación. No añadir nuevos reintentos/timers/intervalos por iniciativa de UI.
4. Cambios RF/seguridad: resumen concreto de campos antes de aplicar; separar de identidad para no enviar PIN/tuning/ACL al editar otra sección. Exponer acción y estado por campo si backend permite resultados parciales.
5. Responsive: dos columnas de pestañas remotas en móvil, wrap completo,44px de objetivo táctil, formulario una columna y acciones visibles al final o barra sticky sin cubrir contenido. En desktop usar ancho suficiente sin comprimir nombres.
6. i18n: claves semánticas para nuevo estado, errores/capacidades/unidades; textos y aria traducidos conjuntamente, plural/locale explícitos, preservar etiquetas técnicas de protocolo cuando sean necesarias. Validar es/en con mensajes largos y cero/desconocido.
7. Regresiones dirigidas posteriores: edición durante WebSocket, A→B incompleto, cero/potencia hardware, duplicados,422/401/503, respuesta aplicada, tuning decimal, ACL sin cambios y navegación teclado. No atribuir a estos mocks validación de firmware.

## Bloqueos de integración y errores del entorno

El servidor virtual conserva en run-output.txt NameError: `_safe_float` is not defined en AdvertHandler, impidiendo poblar normalmente los adverts del fixture. Se inyectaron datos mock únicamente en el Map del contexto para continuar revisando configuración; no se parcheó el módulo ni se oculta el error. Se observó WebSocket conectado; dos errores console corresponden a422 deliberados de reproducción.

Intentos iniciales separados del producto: Chromium spawn EPERM en sandbox, import con ruta errónea `/static/js/modules` corregido a ruta servida `/js/modules`, modal de la propia reproducción interceptando un click de navegación corregido cerrándolo, y print de emoji bajo cp1252 corregido con ensure_ascii. La ejecución final exit0 no incluye esos errores del harness. Se descartó la hipótesis de doble login: el botón HTML1696 es type=button; no se lista como defecto.
